## 0. 结论先行

1. **四者不是四个产品，而是同一条曲线上的四个位置**：能力验证（OpenClaw）→ 组织化（WorkBuddy）→ 产品化（Personal Agent 集群）→ 基础设施化（DeepSeek super-agent）。
2. **竞争焦点从模型转向运行时与治理**：模型能力趋于商品化，真正拉开差距的是调度、记忆、权限、审计与成本可见性。[5]
3. **每一次能力跃迁，都会补上一层治理**：审批、身份、审计、私有化、Auto-review、Mandate/Policy 都是能力可交付的前提，而不是能力的对立面。
4. **企业落地不会从「通用助手」开始**：会从一个有独立交付物、可计量、可审计的单点开始，先在后台站住，再往前台走。
5. **对独立产品最可守的位置是 B（交付型数字员工），不是 A（入口 Copilot）或 C（通用运行时）**：A 容易被平台吞并，C 的壁垒与周期属于大厂/平台团队；B 用别人的运行时，把行业知识、复核、审计和交付做成产品。

## 1. 四个样本：同一条曲线上的四个位置

| 时间 | 样本 | 产品形态 | 关键设计 | 暴露的问题 |
| --- | --- | --- | --- | --- |
| 2026.01 发布，03 月爆发 | OpenClaw | 开源、可自托管的个人 Agent | 长期记忆、约 30 分钟 heartbeat、cron/Webhook、Markdown + SQLite 索引、审批绑定目录与可执行文件 | 安全边界、长任务可靠性、成本与运维责任全在用户 |
| 2026.03 上线，10 月企业版 | 腾讯 WorkBuddy | 办公智能体平台（个人版 → 企业版） | 企业微信入口、统一 Agent 底座、Agent 独立身份与权限继承、审计、可观测、托管智能体（SaaS/VPC/私有化） | 个人提效不等于组织回报；系统打通与放权难 |
| 2026.08—09 密集发布 | Personal Agent 集群（Grok Bot、Muse、Manus 2.0/Cue、dots 等） | 面向个人的常驻 Agent 产品 | 独立云电脑、个人数字身份（邮箱/电话/钱包）、定时与事件触发、审批页、记忆管理 | 可靠性、常识、成本、信任；同质化严重 |
| 2026.10.31 | DeepSeek super-agent 原型 | 常驻 Agent 运行时（Router + Worker） | 事件驱动、订阅直通、计算/状态/环境分离、外部 Watchdog、Ticket/Mandate/Policy 授权模型 | 合成负载验证；单 Router 扩展、多租户与凭据风险未解 |

### 1.1 OpenClaw：把「个人拥有一台能干活的 Agent」变成大众实践

OpenClaw 是一款开源 AI 智能体，能替人执行终端命令、读写文件、收发邮件、管理日程；用户通过自然对话就能派活，不需要懂代码和操作系统。[1] 它更接近一个**可以自行部署和配置的个人 Agent 运行时**：长期记忆、约 30 分钟一次的 heartbeat、任务调度器、cron 与 Webhook，权限与审批可按目录和可执行文件配置；代价是运行环境、配置和安全责任也由用户自己承担。

它留下的遗产有三样：**Agent 可以拥有并操作一台真实电脑**、**Skills 生态可以病毒式扩张**、**IM 可以成为 Agent 的默认入口**。它没解决的是：凭据与提示注入、长任务可靠性、以及「装完之后谁来运维」。原研究引用开发方预印本称其在共同任务上完成率约 42%，该数据只能作方向参考，不能当作生产可用性结论。

### 1.2 WorkBuddy：把能力「组织化」

腾讯 WorkBuddy 于 2026 年 3 月上线，踩着 OpenClaw 的热度进入办公场景。到 10 月 29 日腾讯全球数字生态大会，官方披露：累计完成 **90 亿次任务请求**，企业版落地 **50 多个行业**，覆盖 **50% 的中国企业 500 强、60% 的中国企业 100 强**。[2] 10 月与企业微信深度融合，腾讯文档、腾讯网盘、ima 共享同一套 WorkBuddy Agent 底座。

企业版的四个升级，基本是一份「企业落地需求清单」：[3]

- **开放平台**：兼容第三方 IM、企业内部系统和自研 Agent；
- **企业级安全**：行为可控、过程可溯、数据可管；每个 Agent 有独立身份，权限不超出授权人范围，敏感信息按策略脱敏或阻止进入模型上下文；
- **可观测中心**：让企业能衡量投入与效果；
- **托管智能体 WMA**：云端内核由 Agent 运行时、Harness、模型与企业管理平台四部分组成，提供 SaaS、VPC 专享、私有化三种形态。

一个很有说服力的内部案例是「磐石小O」：把 ERP 系统的 9 个业务、300 多个接口接入 WorkBuddy，员工用对话查经营数据或发起审批，**每次调用继承员工身份与权限，并保留审计记录**。[3] 这句话几乎就是企业 Agent 的全部关键点。

WorkBuddy 自己总结的痛点也很准：**系统难打通、不敢放权、不好管控、难以常驻**；并给出「试用 → 推广 → 沉淀 → 连接 → 自治」的五阶模型。它还引用了一组关键数据：**80% 的员工认为 AI 提升了个人效率，但只有 6% 的组织获得显著业务回报**。个人提效与组织变强之间，隔着的正是治理与流程。[3]

### 1.3 Personal Agent 集群：把「持续委托」产品化

2026 年 8—9 月，海外 Personal Agent 几乎同时发布：Grok Bot、Meta Muse、Manus 2.0/Cue、OpenAI dots，更早还有 Google 的 Gemini Spark。[4][7] 这一代的新意不在「会调工具」，而在**产品组织方式**：围绕一个具体用户，把四样东西整合进同一个产品——

1. **运行内核**：模型 + Harness，负责规划、记忆、调度与工具调用；
2. **独立执行环境**：一台真正属于这个 Agent 的云电脑（独立 Linux 桌面/VM），能像人一样操作浏览器、管理多个标签页；
3. **工具与服务生态**：邮箱、日历、浏览器、支付、企业应用连接器；
4. **数字身份**：独立邮箱、电话号码、钱包，让它能注册服务、验证身份、完成交易。

用户交办任务的主界面因此变了：不再是一段即时对话，而是**任务列表、审批页、计划安排、记忆管理和执行记录**。Agent 会在用户离开后继续工作，按时间、按事件、或按自己的判断被唤醒。

这一代证明了两件事：**「always-on」的个人 Agent 在产品形态上成立**；以及**同质化来得非常快**——当大家都能连邮箱、日历和浏览器时，差异化只剩执行环境质量、身份能力、生态开放度和信任设计。

### 1.4 super-agent：把 Agent 变成「可调度的运行时」

2026 年 10 月 31 日，DeepSeek Harness 团队发布《Towards a More Autonomous Agent System》并开源验证性原型 dsh-superagent。[5] 它要解决的不是「模型会不会写代码」，而是**「一个人同时盯十个 Agent 时，注意力先崩溃」**。

方案是五件套：Router/Worker 双层架构、事件驱动、异步多信道交互、计算与状态及环境分离、外部 Watchdog。关键数字：在约 300 条群聊与 CI 消息（含约 20 个真实工作请求）的合成负载上，p50/p95 完成时间为 **12.4/15.7 分钟**，而带 Subagent 工具的单会话 p95 达 **29.5 分钟**；取消「订阅直通」后 Router 决策数增加约 **30%**、读缓存 token 从 **2323 万涨到 3177 万**；Router 批处理把单个决策分摊的推理时间从 **6.4 秒压到 1.6 秒**。

更值得看的是它的领域模型：Source 产生 Trigger，Trigger 属于 Thread；订阅让同一话题的后续消息**直通**已经在该话题上的 Worker，不再回到 Router；Eval 决定是否接受为新工作；接受后生成 Ticket 与 Mandate（授权：策略版本、范围、强度、匹配规则、发送者身份）；每个 Ticket 有独立的执行会话与目录，交付物回到原来的对话（例如一个 PR）。授权与上下文分离：订阅只送上下文，不授予权限；只有人明确停止才撤销 Mandate。

这套设计的本质，是把「人的注意力」当成稀缺资源来调度：**少占用人的注意力，多交付价值**。它把 Session 从产品概念降级为实现细节——用户只在自己工作的地方（IM、PR）说话，系统自己决定派几个 Worker、谁订阅哪条线程。

局限也很清楚：合成负载、简化环境；单 Router 何时需要水平切分、多实例间 A2A 如何划上下文、云端 Agent 接入本地凭据的注入风险，四个开放问题都没有答案。它是原型，不是产品。

## 2. 六条演化规律

### 规律一：委托长度决定产品形态

| 委托长度 | 代表形态 | 产品组织方式 |
| --- | --- | --- |
| 一问一答 | Chatbot | 以当前会话为中心 |
| 一个明确任务 | 早期 Manus | 云沙箱里跑完一个目标，交付报告/网页/代码 |
| 一段持续委托 | OpenClaw、Personal Agent | 常驻环境 + 触发条件 + 记忆 + 审批 |
| 一个团队的并行委托 | dsh-superagent | 路由层 + 隔离 Worker 池 + 订阅 + 授权域 |

每加长一层，**状态放在哪里、谁来唤醒、谁有权执行、失败谁来兜底**这四个问题就要重新回答一次。产品形态的差异，本质上是这四个答案的组合。

### 规律二：交互面持续外移，Session 退化为实现细节

Chatbot 时代，界面就是对话；Personal Agent 时代，主界面变成任务列表 + 审批页 + 记忆管理；super-agent 时代，人只在 IM 或 PR 里说话，调度、并发、上下文同步都由系统接管。

对产品设计的直接含义是：**不要再把「聊天框」当成主界面**。用户要的是「事情在推进」的可见性（任务状态、审批、执行记录），以及「出问题时能找到人」的确定性。对话框只是入口之一，不是产品本体。

### 规律三：执行环境独立化，从「共享工具」到「每任务一个」

工具调用 → 沙箱 → 云电脑 → 隔离 Worker 池。环境从「共享」到「每人一台」再到「每任务一个」，带来的是隔离性、可回滚性和并发能力，代价是成本与调度复杂度。

WorkBuddy 的 VPC/私有化、Personal Agent 的独立 VM、super-agent 的每 Ticket 独立目录，是同一条路的不同刻度。企业采购时问「数据出不出域」，本质上就是在问这个环境的边界。

### 规律四：能力跃迁一次，治理补一层

- OpenClaw 证明了能力，暴露了安全，于是补**审批**（命令绑定目录与可执行文件）；
- WorkBuddy 要进企业，于是补**身份、权限继承、审计、脱敏、私有化**；
- Personal Agent 要替人对外行动，于是补**Auto-review、权限分层、凭证隔离**；
- super-agent 要并行推进，于是补**Mandate、Policy、订阅与停止语义**。

治理不是「限制能力」，而是**让能力可以被交付、被采购、被追责**。没有治理层的能力，只能停留在 demo 和极客玩具。

### 规律五：计费单位随委托长度上移

开源/云「卖铲」（算力、镜像、API Key）→ 企业版席位/订阅 → 数字员工按岗位/任务/成果计费。

当价值从「帮你写一段话」变成「替你完成一件有外部结果的事」（PR 通过测试、对账平了、工单闭环、合规报告过审），计费单位自然会从 token 转向**任务、结果或人头**。[10] 这对创业公司的含义是：**越早把交付物定义清楚，越早能算清 ROI，也越早能收费**。

### 规律六：组织两端同时生长

一端是「超级个体/一人公司」：一个人加一群数字员工，能撑起过去十个人的活；另一端是「超级组织」：同一套运行时被复制到成百上千个岗位，靠治理与流程放大。

这两端用的是同一套技术栈，区别只在治理强度。**产品如果只能服务一端，增长会很快遇到天花板。**

## 3. 未来 12—24 个月的趋势

1. **技术栈：运行时分层与「Agent OS」化。** 入口层、编排层、执行层、记忆层、工具层、治理层逐渐分离；Agent 身份与权限成为标准件；MCP 管工具、A2A 管 Agent 间协作；记忆、任务轨迹与评测体系成为资产；按任务/租户/Agent 的可观测与成本核算成为企业采购项。[8][9]
2. **产品形态：个人免费入口 + 企业数字员工 + 平台底座。** 中国更可能是「生态内嵌」（每个超级 App 长出自己的 Agent），而不是一个通用助手通吃；企业侧「数字员工」按岗位/任务/成果计费；任务列表 + 审批 + 记忆管理成为主界面。
3. **商业与组织：从 token 到结果，从工具到编制。** 席位 + 用量 + 结果分成的混合计价会出现；「Agent 管理者」进入组织；安全事件会推动监管、保险与合同条款，「可审计」从卖点变成门槛。
4. **可证伪的信号。** 12 个月内是否出现事实上的 Agent 身份/权限标准；企业客单价是否从席位转向结果/任务；IM 平台是否开放 Agent 目录与结算；是否发生大规模 Agent 安全事故；单 Router 水平扩展是否成熟。

## 4. 三种生意：A 入口、B 交付、C 底座

| 形态 | 是什么 | 价值 | 壁垒 | 适合谁 | 收费 |
| --- | --- | --- | --- | --- | --- |
| A. 入口型 Copilot | 嵌在 IM/OA/CRM 里的助手 | 低门槛、上手快、覆盖广 | 入口与生态，容易被平台吞并 | 大平台、ISV | 席位/订阅 |
| B. 交付型数字员工 | 有独立交付物的 Agent（PR、工单、对账、合规报告、客服闭环） | 可计量、可审计、直接省人天 | 行业 know-how + 交付质量 | 创业公司、垂直行业 | 按任务/结果 |
| C. 底座型 Agent 运行时 | 私有化/VPC 的运行时 + 治理 + 集成 + 技能市场 | 长期壁垒、可复制 | 稳定性、治理、生态 | 企业 IT/平台团队 | 订阅 + 用量 |

**最容易被低估的是 B，最容易被高估的是 A。** 入口型产品看起来离用户最近，但没有独立交付物就很难单独计价，最终会变成平台的一个功能；交付型产品看起来窄，但每一单都能说清楚「省了多少人天/避免了多少停摆」，反而最容易收到钱。

## 5. 选点与切入节奏

### 5.1 四个标准：高频 × 必经 × 可度量 × 可审计

- **高频**：每天都要处理，而不是三年一次；高频小痛点能卖成工具，低频只能卖成保险。
- **必经**：卡在客户不得不走的流程上（发布、交付、审批、对账、审计），绕不开。
- **可度量**：出事时能说清代价（停摆多久、多花多少人天、审计是否通过）。
- **可审计**：Agent 的每一步能追溯、能回滚、能授权到人——这是 Agent 区别于传统软件的新增要求。

四个都满足的点，才是「Agent 原生」的生意；只满足前两三个的，往往还是传统自动化或 Copilot 的生意。

### 5.2 买家的真实心态：只肯给「短皮带」

G2 对 3,222 条企业 Agent 评价的分析很能说明问题：**77% 的买家信任 Agent，但只有 7% 愿意给它完全自主权**；60% 选择「有护栏的自主」，21% 只给有限自主，11% 坚持人在回路；25% 的差评集中在部署与复杂度；完全采用率从 2024 年的 68% 降到 2026 年的 55%；同时已有 66% 的组织在有限或规模化生产环境中运行 Agent。[6]

企业不是不信任 Agent，而是只肯给「短皮带」。这直接决定了切入方式：**先用护栏换信任，再用结果换放权**。这也回应了「企业不为 AI 付费，除非能带来实际收益」的判断——收益必须可度量、可归因。

### 5.3 切入节奏：单点交付 → 团队复制 → 组织底座

1. **选一个单点**：优先研发（PR/发布/CI）、财务（对账/报销）、客服（工单闭环）、合规（审查报告）——交付物天然存在、天然可审计。
2. **先 observe，再建议，后自动**：用 2—4 周只记录「Agent 会怎么做」，积累轨迹与评测，再开人在回路的自动执行。
3. **把权限设计进产品**：Agent 继承发起人身份与权限、敏感信息脱敏、高风险动作审批、失败可回滚、全程审计。
4. **用可度量指标做 ROI**：节省人天、停摆时长、一次通过率、审计通过率；不要用「感觉好用」。
5. **团队级复制**：同一运行时接更多 Source（IM、工单、CI），再走向组织级治理与技能市场。

### 5.4 五种常见失败模式

1. **做成「又一个聊天入口」**：没有独立交付物，无法计价，最终被平台吞并。
2. **按 token 卖**：客户算不清 ROI，采购无法立项。
3. **过度定制**：每个客户一套流程，项目制交付，无法复制。
4. **只做 demo 不做评测**：上线即翻车，一次事故毁掉信任。
5. **忽视权限与审计**：过不了安全评审，或者过了也不敢放权。

| 趋势结论 | 对 `product-direction.md` 的含义 | 我们的选择 |
| --- | --- | --- |
| 竞争从模型转向运行时/治理 | 不自研通用 runtime；用现成模型与编排，把治理做进垂直产品 | 做 B 交付型数字员工，不做 C 底座 |
| 委托变长、界面外移 | 主界面是任务列表/审批/执行记录；IM/PR 是入口，不是聊天框 | 投标检查队列 + 复核 + 审计日志 |
| 每次能力跃迁补治理 | 审批、身份、审计、回滚从 v0 就有，而不是上线后再补 | 先收费试点，先过安全评审 |
| 计费单位随委托长度上移 | 按份/任务/结果计价，不按 token | 按份/按任务/年费 + 用量 |
| 企业从可度量、可审计的单点开始 | 选高频、必经、可度量、可审计的楔子，不做通用助手 | 工程投标合规检查；合同抽取/客服备选 |
| B 被低估、A 被高估、C 壁垒最高 | 做垂直交付，不做入口 Copilot/通用平台 | B；不碰 A/C |

**取舍说明**：趋势研究说「运行时与治理是下一个战场」，但这是对大厂/平台团队说的。创业团队如果去做 C（通用运行时），会同时面对 WorkBuddy WMA、云厂商和开源的竞争；做 A（入口 Copilot）会被平台吞并。最可守的是 B：用别人的 runtime，把行业知识、复核、审计和交付做成产品。这与 `product-direction.md` 第 2、3 节的垂直判断一致。

**对首选楔子的支持**：工程投标合规检查满足「重复发生 × 必经 × 可度量 × 可审计」四项，且 AI 做的是「读/比/列缺口」而不是替人做专业判断；四代样本的失败模式（OpenClaw 的安全/运维、WorkBuddy 的系统打通/放权、Personal Agent 的同质化、super-agent 的多租户/凭据）正好对应产品的「窄、可复核、可审计、业务人员可用」设计。法律只保留「抽取/义务清单」，不做判断型审查。

**明确不做**：通用桌面 Agent（OpenClaw 式安全与运维责任）、通用办公助手（WorkBuddy/千问的入口战场）、通用 Bot（Personal Agent 式同质化）、无监督自主（G2 仅 7% 买家愿意给完全自主权）。
